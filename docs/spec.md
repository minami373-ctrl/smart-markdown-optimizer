# 仕様書：見切り品ダイナミックプライシング・シミュレーター

> この文書が唯一の正（北極星）。実装・テストで迷ったらここに戻る。
> ここに無い挙動は足さない。不足・矛盾を見つけたらこの文書を先に直す。

## 1. 概要 / 目的

スーパーの惣菜部門でのアルバイト経験（値引きが「19時＝3割引・20時半＝半額」のように
固定化されており、雨の日は売れ残り＝廃棄ロス、晴れの日は早期完売＝機会損失が起きる）を
出発点にした、**ベイズ統計による動的値引き最適化のシミュレーションアプリ**。

過去の購買実績・天気・曜日・イベント情報を事前分布とし、営業中の購入ログ（尤度）で
逐次ベイズ更新した事後分布から、目標廃棄率を満たす最適な値引き率とタイミングを提案する。
実店舗との連携は行わず、**乱数によるシミュレーションとして動作を確認できるデモ**として作る
（就活ポートフォリオとして技術力を見せることが目的）。

## 2. スコープ

### やること

- 商品（初期状態は唐揚げ・おでん・寿司の3件）それぞれについて、天気・曜日・イベント有無に
  応じた事前分布（基準需要）を持つ
- 画面から商品を追加・削除できる（12条件ぶんの事前分布は「基準需要」1つの入力から自動計算する）
- シミュレーション開始 → 営業時間を圧縮したステップ単位で購入ログを乱数生成
- 新しい購入ログが入るたびにベイズ更新し、事後分布から値引き率を提案
- 目標廃棄率は画面上で変更可能
- シミュレーション終了後、実績廃棄率と達成可否を履歴として保存・一覧表示

### やらないこと（今回対象外）

- 実店舗のPOSレジ・在庫システムとの連携
- 実際の天気APIとの連携（天気は選択肢から選ぶダミー）
- 複数店舗・複数部門への対応
- ユーザー認証・ログイン画面
- モバイル画面の作り込み（PC幅のみ想定）
- デプロイ・Docker化・CI

## 4. 画面仕様

### ① シミュレーション画面 `/`

- **目的**：条件を設定して営業をシミュレーションし、リアルタイムの値引き提案を確認する
- **表示・入出力**
  - 条件設定：天気（晴れ／曇り／雨）・曜日（平日／休日）・イベント有無（チェックボックス）・
    目標廃棄率（スライダー、0〜10%、既定3%）
  - `営業開始` ボタン（主要アクション）
  - 開始後、3商品それぞれのカードに「現在の推奨値引き率」「事後分布の平均残数」を表示し、
    購入ログが生成されるたびに自動更新される
  - 各カードに、その商品の**需要率の事後分布（ガンマ分布）の確率密度曲線**をグラフで表示する。
    開店直後は山が低く横に広い（不確実性が大きい）状態から、ステップが進み購入ログが
    蓄積されるにつれて山が高く鋭くなっていく（確信度が上がる）様子を可視化する。
    このグラフは`/history`の値引き率推移グラフとは別物（今回のライブ画面専用。
    分布パラメータ(alpha/beta)は過去分を保存しないため、履歴画面では表示しない）
  - 終了後、各商品の「実績廃棄率」「目標達成可否」を表示
  - 商品カードの下に**在庫推移グラフ**（横軸=ステップ、縦軸=残り在庫数、商品ごとに色分けした
    折れ線）を1つ表示する。`/history`の値引き率推移グラフ（`RateChart`）と同じ描画方式で、
    こちらは値引き率ではなく `remaining_stock` の推移を見せる。開始前（`detail`が無い状態）は
    表示しない。進行中は現在の`visibleStep`までを描画し、他のカードと同じタイミングで
    自動更新される（新しいAPI呼び出しは追加しない。既存の`StepOut.remaining_stock`をそのまま使う）。
    系列名（凡例）は`RateChart`と同じく`detail.finals`（実行時点のスナップショット）から解決し、
    実行中に別画面で商品が削除されても他のカードと表示名がずれないようにする。
    `remaining_stock`が無い/nullのステップは「在庫が減っていない」と誤読されないようnullのまま
    描画し（線を途切れさせる）、満タン（初期在庫）にフォールバックしない
- **操作と結果**
  - `営業開始` → シミュレーションが自動進行（全40ステップ、1ステップ0.5秒間隔で画面更新）。
    二重開始はボタンを無効化して防ぐ
  - 終了時、結果を `SimulationResult` として保存し、`/history` から見られるようにする

### ② 商品設定画面 `/products`

- **目的**：商品の事前分布パラメータ（天気・曜日・イベント別の基準需要）を確認し、
  商品を追加・編集・削除する
- **表示要素**
  - 商品を一覧表示。各商品の天気×曜日×イベントの組み合わせごとの基準需要（λ値）と、
    **値引き感度**（`elasticity`。値引き10%あたり需要が何倍になるか）を表示する
    読み取り専用の一覧（12条件の個別編集はしない）
  - `商品を追加` フォーム：商品名（テキスト）・初期在庫（数値・1以上）・値引き感度（数値・
    0より大きい）・基準需要（数値・0より大きい。「平日・晴れ・イベントなしの日、1ステップに
    平均何個売れそうか」の目安値）の4項目のみ入力する
  - 各商品の一覧行に `編集` ボタンと `削除` ボタン
- **操作と結果**
  - `商品を追加` → 入力した基準需要から §5.4 の計算式で12条件ぶんの事前分布を自動生成し、
    商品を作成する。作成後、一覧が更新される
  - `編集` → その商品の行が追加フォームと同じ4項目の入力欄に変わる（インライン編集）。
    4項目とも**現在の値をプリフィルした状態**で開く（商品名・初期在庫・値引き感度はそのままの値、
    基準需要だけは保存済みの `晴れ_平日_なし` の alpha を逆算して
    （`alpha ÷ 2.4`。§5.4 の倍率 晴れ1.2×平日1.0×イベントなし1.0×beta2.0 の逆算）表示する）。
    `保存` を押すと、新しい基準需要で12条件ぶんの事前分布を作り直し、商品名・初期在庫・
    値引き感度とあわせて上書きする。**API（PATCH）は部分更新ではなく全項目の上書き**で、
    フォームで直さなかった項目もプリフィルされた現在値をそのまま送信する
    （サーバー側は「送られなかった項目は前の値を保持する」という差分更新をしない）
  - `削除` → 確認なしで即座に削除する（このアプリはローカル単一ユーザー・デモ用途のため）。
    削除した商品が過去のシミュレーション履歴に含まれていても、履歴の表示は壊さない
    （商品名は「?」として表示される。§5.2 のとおり `Product` の行を消すだけで、
    過去の `PurchaseLog` 等は消さない）

### ③ 履歴画面 `/history`

- **目的**：過去のシミュレーション結果を振り返る
- **表示要素**：実行日時・条件（天気/曜日/イベント）・目標廃棄率・商品ごとの実績廃棄率・
  達成可否を一覧表示（新しい順）
- **操作と結果**：行をクリックすると、その回の値引き率の推移グラフ（横軸=ステップ、
  縦軸=推奨値引き率、商品ごとに色分け）を表示する。画面遷移はしない（同一画面内に展開）

### ④ 機会損失分析画面 `/opportunities`

- **目的**：値引きを一切せずに閉店前に完売してしまった商品（＝在庫不足で売り逃した
  可能性がある商品）を、過去のシミュレーション履歴全体から見つけて一覧にする
- **表示要素**：「早期完売（値引きなし）」に該当した商品を、推奨追加在庫数（平均）の
  多い順に**最大10件**表示する。1行につき：順位・商品名・該当回数・平均完売ステップ
  （例 `18/40`）・推奨追加在庫数。該当商品が無ければ
  「値引きなしで早期完売した商品はまだありません。」と表示する
- **操作と結果**：読み取り専用（クリックしても遷移・展開しない）

## 5. 処理フロー

### 5.1 事前分布の設定（seedデータ）

商品ごとに、天気（晴れ/曇り/雨）×曜日（平日/休日）×イベント有無の**12通り**の組み合わせに
対して基準需要（ガンマ分布の形状パラメータ相当）をあらかじめ `seed/products.json` に持つ。

### 5.2 シミュレーション実行（`services/simulation.py`）

**入力**：天気・曜日・イベント有無・目標廃棄率

1. 選択条件に対応する事前分布（ガンマ分布のパラメータ α, β）を各商品ごとに読み込む
2. 全40ステップ（営業時間10:00〜21:00相当を圧縮）を1ステップずつ進める。各ステップで：
   a. 現在の値引き率と値引き感度から購入確率を補正し、ポアソン分布で購入個数を乱数生成
      （**乱数シードは `SimulationRun.id` から決定的に導出**し、同じ条件・同じ実行順なら
      同じ結果になるようにする）
   b. 生成した購入ログをガンマ-ポアソン共役更新の尤度として事後分布（α', β'）を更新
   c. 残り時間・現在庫（初期在庫－累計購入数）・事後分布の期待値から、目標廃棄率を
      満たすために必要な値引き率を計算（MAP推定）。前回提案から**5%pt以上**変化した場合のみ
      新しい提案として記録・表示する
3. 40ステップ終了時、各商品の最終在庫 ÷ 初期在庫を実績廃棄率とし、目標廃棄率以下なら達成、
   超えていれば未達とする

**出力**：ステップごとの `PurchaseLog` と `DiscountRecommendation`、終了時の `SimulationResult`
**エラー時**：初期在庫が0の商品は購入ログ生成をスキップする（ゼロ除算を避ける）

### 5.3 値引き提案の計算式

```
必要値引き率 = f(事後分布の期待残数, 残りステップ数, 目標廃棄率, 商品の値引き感度)
```

- 事後分布の期待残数が「残り時間で目標廃棄率以内に売り切れる見込み数」を上回っていれば、
  超過分を値引き感度で割り戻した値引き率を提案する
- 値引き率は 0%〜70% の範囲に丸める（70%を超える値引きは提案しない）

### 5.4 商品追加時の事前分布の自動生成（`services/prior.py`）

**入力**：基準需要（`base_demand`。平日・晴れ・イベントなしの日の1ステップあたり平均需要）

天気・曜日・イベント有無の全12通りの組み合わせについて、`seed/products.json` を作った ときと
同じ倍率テーブルを使い、`alpha = base_demand × 天気倍率 × 曜日倍率 × イベント倍率 × beta`、
`beta = 2.0`（固定）として各条件のガンマ分布パラメータを計算する。

| 区分 | 倍率 |
|---|---|
| 天気：晴れ | 1.2 |
| 天気：曇り | 1.0 |
| 天気：雨 | 0.7 |
| 曜日：平日 | 1.0 |
| 曜日：休日 | 1.3 |
| イベント：なし | 1.0 |
| イベント：あり | 1.4 |

**出力**：`condition_key()`（§5.2 と同じ形式）をキーにした12エントリの辞書
**エラー時**：`base_demand <= 0` は呼び出し元（API）でバリデーションエラーとして弾き、
この関数自体はガードしない（純関数として「正しい入力なら常に正しい出力」に留める）

### 5.5 機会損失の検出と推奨追加在庫数（`services/opportunity.py`）

**入力**：`SimulationRun`（`status="finished"`のもの全件）ごとの、商品別の
`PurchaseLog`（ステップごとの`quantity`）と`DiscountRecommendation`（値引き率）

**処理**（1つの `run × product` の組ごとに判定する純関数）

1. ステップ0から順に見て、**一度でも `recommended_rate > 0` になった時点で対象外**にする
   （値引きが1回でもあれば「値引きなしで完売」ではない）
2. 値引きが一度も無いまま、**残り在庫が0になったステップ（`sellout_step`）** を探す。
   最後まで（40ステップ目まで）売り切らなければ対象外
3. `sellout_step` が **37以下**（＝閉店の3ステップ以上前）のときだけ「早期完売」として扱う
   （終了間際の完売は正常な在庫量と見なし、対象に含めない）
4. 早期完売と判定された場合、`sellout_step` までの平均販売ペースを40ステップぶんに
   引き延ばして、必要だったと見積もられる在庫数との差分を計算する：

```
steps_to_sellout = sellout_step + 1
推奨追加在庫数 = round(初期在庫 × (40 - steps_to_sellout) / steps_to_sellout)
```

**集計**：商品ごとに、該当した `run` 全件から「該当回数」「平均完売ステップ」
「推奨追加在庫数の平均」を求め、**推奨追加在庫数の平均が大きい順に上位10件**を返す
（該当0件の商品は結果に含めない）

**出力**：`{product_id, product_name, occurrence_count, avg_sellout_step, avg_suggested_increase}` の配列
**エラー時**：完了済みの `SimulationRun` が1件も無ければ空配列を返す（エラーにしない）

## 6. データモデル

### Product（商品。初期状態は3件・seed投入。画面から追加・削除できる）

| 項目 | 型 | 必須 | 制約・説明 |
|---|---|---|---|
| id | int | ○ | 主キー |
| name | str | ○ | 商品名（唐揚げ／おでん／寿司） |
| initial_stock | int | ○ | 1日の初期在庫数 |
| elasticity | float | ○ | 値引き10%あたりの需要増加倍率 |
| prior_demand | str | ○ | JSON文字列。`{"晴れ_平日_なし": {"alpha":.., "beta":..}, ...}` の12キー |

### SimulationRun（1回の営業シミュレーション）

| 項目 | 型 | 必須 | 制約・説明 |
|---|---|---|---|
| id | int | ○ | 主キー |
| weather | str | ○ | 晴れ／曇り／雨 |
| day_type | str | ○ | 平日／休日 |
| has_event | bool | ○ | イベント有無 |
| target_waste_rate | float | ○ | 目標廃棄率（0〜0.10） |
| status | str | ○ | running／finished |
| started_at | datetime | ○ | 開始時刻 |
| finished_at | datetime | | 終了時刻。running中はnull |

### PurchaseLog（購入ログ）

| 項目 | 型 | 必須 | 制約・説明 |
|---|---|---|---|
| id | int | ○ | 主キー |
| run_id | int | ○ | `SimulationRun.id` |
| product_id | int | ○ | `Product.id` |
| step | int | ○ | 0〜39 |
| quantity | int | ○ | このステップで生成された購入個数 |

### DiscountRecommendation（値引き提案の履歴）

| 項目 | 型 | 必須 | 制約・説明 |
|---|---|---|---|
| id | int | ○ | 主キー |
| run_id | int | ○ | `SimulationRun.id` |
| product_id | int | ○ | `Product.id` |
| step | int | ○ | この提案が出たステップ |
| recommended_rate | float | ○ | 提案値引き率（0〜0.70） |
| posterior_mean | float | ○ | このときの事後分布の期待残数 |

### SimulationResult（終了時の実績）

| 項目 | 型 | 必須 | 制約・説明 |
|---|---|---|---|
| run_id | int | ○ | `SimulationRun.id` |
| product_id | int | ○ | `Product.id` |
| final_waste_rate | float | ○ | 実績廃棄率（終了在庫 ÷ 初期在庫） |
| achieved | bool | ○ | 目標廃棄率以下だったか |

## 7. 受け入れ条件

- [ ] `営業開始` を押すとシミュレーションが自動進行し、画面が購入ログの発生に合わせてリアルタイムに更新される
- [ ] 天気を「雨」にすると「晴れ」より基準需要（λ）が下がり、より早いステップで値引き提案が出る
- [ ] 目標廃棄率を画面で変更すると、同じ条件でも提案される値引き率の計算結果が変わる
- [ ] 同じ `SimulationRun.id` からシミュレーションを実行すると、乱数が決定的になり毎回同じ購入ログ・結果になる
- [ ] シミュレーション終了後、各商品の実績廃棄率と目標達成可否が表示され、`SimulationResult` として保存される
- [ ] `/history` で過去の回を選ぶと、その回の値引き率推移グラフ（商品別）が表示される
- [ ] 3商品（唐揚げ・おでん・寿司）それぞれ独立に値引き提案が計算され、互いに影響しない
- [ ] `/products` で基準需要を入力して商品を追加すると、一覧に12条件ぶんの事前分布が
      自動生成された状態で追加される（天気「晴れ」は「雨」より基準需要が高い値になる）
- [ ] 追加した商品は `/` のシミュレーション画面にもカードが増え、他商品と同様に値引き提案が計算される
- [ ] 商品を削除すると一覧から消える。削除しても、その商品を含む過去のシミュレーション履歴の
      表示はエラーにならない（商品名が「?」になるだけ）
- [ ] `/opportunities` は、値引きを一度もせず閉店3ステップ以上前に完売した商品だけを対象にし、
      推奨追加在庫数の平均が大きい順に最大10件表示する
- [ ] 一度でも値引きされた商品や、閉店間際（37ステップ超）に完売した商品は `/opportunities` の対象外になる
- [ ] 該当する商品が無ければ「値引きなしで早期完売した商品はまだありません。」と表示される（エラーにしない）
- [ ] `/products` で商品を編集して基準需要を変えると、12条件ぶんの事前分布が新しい値で作り直される
- [ ] 編集フォームを開いたとき、基準需要の初期値は保存済みの事前分布から逆算した値になる
- [ ] シミュレーション実行中、在庫推移グラフが商品ごとの残り在庫数を折れ線で表示し、
      ステップが進むごとに描画範囲が伸びていく（開始前は表示されない）
