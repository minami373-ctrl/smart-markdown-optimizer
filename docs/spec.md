# 仕様書：見切り品ダイナミックプライシング・シミュレーター

> この文書が唯一の正（北極星）。実装・テストで迷ったらここに戻る。
> ここに無い挙動は足さない。不足・矛盾を見つけたらこの文書を先に直す。

## 1. 概要 / 目的

スーパーの惣菜部門でのアルバイト経験（値引きが「19時＝3割引・20時半＝半額」のように
固定化されており、雨の日は売れ残り＝廃棄ロス、晴れの日は早期完売＝機会損失が起きる）を
出発点にした、**ベイズ統計による動的値引き最適化のシミュレーションアプリ**。

過去の購買実績・天気・曜日・イベント情報を事前分布とし、営業中の購入ログ（尤度）で
逐次ベイズ更新した事後分布から、目標廃棄率を満たす最適な値引き率とタイミングを提案する。
実店舗との連携は行わず、**乱数によるシミュレーションとして動作を確認できるデモ**として作る
（就活ポートフォリオとして技術力を見せることが目的）。

## 2. スコープ

### やること

- 商品（初期状態は惣菜売り場の**12件・3種類**。2026-11-26改訂。§2.1）それぞれについて、天気・曜日・イベント有無に
  応じた事前分布（基準需要）を持つ
- 画面から商品を追加・削除できる（12条件ぶんの事前分布は「基準需要」1つの入力から自動計算する）
- シミュレーション開始 → 営業時間を圧縮したステップ単位で購入ログを乱数生成
- 新しい購入ログが入るたびにベイズ更新し、事後分布から値引き率を提案
- 目標廃棄率は画面上で変更可能
- シミュレーション終了後、実績廃棄率と達成可否を履歴として保存・一覧表示
- **学習の継続**：シミュレーション終了時点の事後分布を、同じ条件（天気・曜日・イベント有無）の
  次回シミュレーションの事前分布として引き継ぐ（同じ条件で繰り返すほど値引き提案の精度が上がる）
- 過去の履歴全体から、在庫不足（`/opportunities`）・在庫過多（`/overstock`）の両方を検出する
  （2つは互いに鏡像。前者は早期完売、後者は値引き上限まで下げても売れ残った商品を対象にする）
- **2026-08-15追加**：同じ乱数の元で「固定スケジュール値引き（19時=3割引・20時半=半額）」
  と「今の動的値引き」を両方シミュレーションし、廃棄率・推定売上を比較する（`/compare`。§5.9）。
  企画の出発点（§1）そのものを実際の数字で裏付けるための機能
- **2026-08-15追加**：過去の全シミュレーション履歴から、天気・曜日・イベント有無の条件ごとに
  値引きが平均何ステップ目から始まっているかを集計する（`/timing`。§5.10）。「雨の日は値引きが
  早まる」という主張を、履歴の蓄積で裏付けるための機能

### 2.1 作り直し第1弾（2026-11-26）

最初の版は「ベイズ更新で値引き率を計算できること」を見せる技術デモで、図にも画面にも
**売り場で動く人（値引きを決めて貼るナイトマネージャー、買うお客さん）が出てこない**ことが
課題だった。中心の逐次ベイズ更新（事前分布 → 購入のたびに更新 → 事後分布、学習の継続）は
変えずに、まわりを実際の惣菜売り場の業務に合わせて作り直す。第1弾は次の4つを順に行う
（1つ終えるごとに仕様書 → 実装 → テスト → コミット）：

1. **商品を12件・3種類にし、営業時間を10:00〜22:00にする**（この節で反映済み）
2. 値引きの段階を「30%引き → 半額 → ズバリ引き（21時以降、値段を直接決める）」にする
3. ナイトマネージャーの承認（シミュレーション条件として再現）と、売り場モニター画面
4. 条件に「長期休み」を追加する

**商品の種類**（`Product.category`）：売り場での売れ方の違いを、種類ごとの値引き感度
（`elasticity`）の差として表す。

| 種類 | seedの商品 | 売れ方（売り場での観察） | 値引き感度の目安 |
|---|---|---|---|
| 弁当・丼 | 唐揚げ弁当・カツ丼・天丼・ロコモコ丼 | 30%引きではまだ残るが、半額になるとほぼ売れる | 高め（0.18） |
| 揚げ物の単品 | ロースカツ・アジフライ・とり天・メンチカツ | 半額になっても結構残る | 低め（0.06） |
| 軽食・つまみ | 焼き鳥・たこ焼き・ポテト・コロッケ | 30%では動かず、半額になってから売れる | 中くらい（0.14） |

商品名は一般的な名前にし、特定の店舗名は書かない。

## 4. 画面仕様

### 全画面共通：ダークモード切り替え

- **目的**：見た目の完成度（ポートフォリオとしての見せ方）を上げる。機能追加ではなく表示のみの変更
- **表示要素**：ナビゲーションバーの右端に切り替えボタン（`🌙 ダーク` / `☀️ ライト`。現在のモードから
  「切り替えた後どうなるか」を示すラベルにする）
- **初期状態の決め方**（優先順）：
  1. `localStorage`に保存済みの選択（`theme` キー、値は`"light"`か`"dark"`）があればそれに従う
  2. 無ければOSの設定（`prefers-color-scheme: dark`）に従う
  3. どちらも無ければライトモード
- **操作と結果**：ボタンを押すとモードが切り替わり、`document.documentElement`の`data-theme`属性
  （`"light"`/`"dark"`）が変わって配色が変わる。選択は`localStorage`に保存され、次回訪問時も
  保持される（ページをリロードしても消えない）
- **配色**：既存のCSS変数（`--brand` `--bg` `--panel` `--ink` `--sub` `--line` `--ok` `--warn`）を
  ダークモード用に上書きする。個別コンポーネントの色分岐（`.insight-banner`等）は書かない。
  現状リテラルで直書きされている繰り返し色（`.tag.ok`・`.tag.warn`・`.insight-banner`の背景、
  ボタンの無効状態の背景）は、この対応の前提として新しいCSS変数（`--ok-weak` `--warn-weak`
  `--disabled`）に切り出す（クラス定義自体は変えず、参照先を変数に差し替えるだけ）。
  `.product-card`の背景色（`#fffefc`）は`--panel`とほぼ同色のため、新しい変数を作らず
  `--panel`をそのまま使うよう統合する
- **初回表示時のちらつき防止**：Reactのマウントを待つと保存済み選択やOS設定の反映が
  一瞬遅れ、ライト→ダークの切り替わりが見えてしまう（FOUC）。`index.html`にインライン
  スクリプトを置き、`data-theme`属性をJSバンドルの読み込みより前に同期的に適用する
  （`frontend/src/lib/theme.ts`の`getInitialTheme`と同じ優先順位のロジックをここだけ重複させる。
  ビルド前に実行する必要があるため）
- **Chart.jsのグラフ（在庫推移・学習曲線・値引き率推移）**：canvasへの直接描画のためCSS変数を
  追従できず、目盛り・グリッド線の色が既定のグレーのままだとダーク背景で見づらくなる。
  `document.documentElement`の`data-theme`属性を`MutationObserver`で購読するフック
  （`frontend/src/lib/useTheme.ts`の`useTheme`）を使い、切り替えのたびに目盛り・グリッド線・
  凡例の色を再計算する（`chartAxisColors`）。確率密度曲線（`DistributionChart`）は軸自体を
  非表示にしているため対象外

### 全画面共通：分析結果バナー

- **目的**：`/opportunities`（機会損失分析）・`/overstock`（過剰在庫分析）は自分から開かないと
  結果が見えないため、該当がある間はどのページを開いていても気づけるようにする
- **表示要素**：ナビゲーションバーの下に、該当件数が1件以上ある間だけ帯状のバナーを表示する。
  新しいAPIは追加せず、既存の`GET /api/opportunities`・`GET /api/overstock`をアプリ起動時に
  1回ずつ呼び、それぞれの配列の件数を見るだけ（ページ遷移のたびに呼び直さない）
  - 在庫不足（`/opportunities`が1件以上）→「在庫不足の可能性がある商品が{n}件あります。」＋
    `/opportunities`への`詳しく見る →`リンク
  - 過剰在庫（`/overstock`が1件以上）→「過剰在庫の可能性がある商品が{n}件あります。」＋
    `/overstock`への`詳しく見る →`リンク
  - 両方とも0件ならバナー自体を表示しない。両方とも1件以上あれば2行とも表示する
- **エラー時**：どちらかの取得に失敗しても例外を投げず、そのバナー行だけ表示しない
  （取得できなかった方を「0件」と区別せず、単に出さない。アプリ全体を止めない）
- **操作と結果**：`詳しく見る →`をクリックすると該当ページへ遷移する（画面遷移のみ。バナー自体に
  削除・既読化などの操作は無い）

### ① シミュレーション画面 `/`

- **目的**：条件を設定して営業をシミュレーションし、リアルタイムの値引き提案を確認する
- **表示・入出力**
  - 条件設定：天気（晴れ／曇り／雨）・曜日（平日／休日）・イベント有無（チェックボックス）・
    目標廃棄率（スライダー、0〜10%、既定3%）。スライダーの隣に**プリセットボタン**
    （`0%` `3%` `5%` `10%`）を置き、押すとスライダーの値がそのまま切り替わる
    （スライダー操作の手間を減らすだけの補助UI。新しい状態は持たず、既存の`targetWasteRate`を
    直接更新する）
  - `営業開始` ボタン（主要アクション）
  - **連続実行**（副次アクション）：回数（数値入力・1〜10の整数・既定5）と `連続実行` ボタン。
    整数以外や範囲外の値はボタンを無効化する。現在の条件設定（天気・曜日・イベント有無・
    目標廃棄率）のまま、同条件でシミュレーションを指定回数**直列で**（1回ずつ完了を待って
    次を開始）実行する。「学習の継続」（§2）の効果を連続実行で分かりやすく見せるための機能で、
    新しいバックエンドAPIは追加しない
    （既存の`POST /api/simulations`をN回呼ぶだけ）
  - **現在の時刻**：進行中のステップ（`visibleStep`）を、営業時間`10:00`〜`22:00`（2026-11-26改訂。1ステップ18分。40ステップで
    圧縮。§5.2）に対応する時刻表示（`HH:MM`）に変換して、商品カードの上に1つだけ表示する
    （例 `現在 19:00`）。値引きは`30%引き`＝19時ごろ、`半額`＝20時半ごろ、という元の企画の
    出発点（§1）通りの対応が、シミュレーション中に実際に確認できるようにするための表示。
    開始前（`detail`が無い）は表示しない
  - **ズバリ引きの承認（2026-11-26追加。§5.11）**：条件設定に「ズバリ引きの承認（ナイトマネージャー）」の
    セレクト（`すぐ承認`／`18分後`／`36分後（忙しい）`／`54分後（1人で回している）`。既定は`すぐ承認`）を
    置き、`approval_delay_steps`（0〜3）として`POST /api/simulations`に送る。連続実行も同じ値を使う
  - **売り場モニター（2026-11-26追加）**：シールを貼る代わりにお客さんに見せる表示。開始後、現在の時刻の
    下に、全商品の「商品名・今の値引き（`30%引き`／`半額`／`ズバリ ¥190`）・値引き前の値段（打ち消し線）と
    値引き後の売値」を一覧で出す。売値は30%引き・半額なら1円単位で四捨五入、ズバリ引きは§5.3の10円単位の
    値段。値引きの無い商品は値段だけ、在庫0の商品は`売り切れ`。**モニターに出すのは承認済みの値引き
    （`applied_rate`）だけ**で、承認待ちのズバリ引きは出さない（`components/MonitorBoard.tsx`）
  - 開始後、各商品のカードに「現在の推奨値引き率」「事後分布の平均残数」を表示し、
    購入ログが生成されるたびに自動更新される
  - 各カードに、その商品の**需要率の事後分布（ガンマ分布）の確率密度曲線**をグラフで表示する。
    開店直後は山が低く横に広い（不確実性が大きい）状態から、ステップが進み購入ログが
    蓄積されるにつれて山が高く鋭くなっていく（確信度が上がる）様子を可視化する。
    このグラフは`/history`の値引き率推移グラフとは別物（今回のライブ画面専用。
    分布パラメータ(alpha/beta)は過去分を保存しないため、履歴画面では表示しない）
  - 終了後、各商品の「実績廃棄率」「目標達成可否」を表示
  - **単価（`Product.unit_price`）が設定されている商品だけ**、終了後に「推定売上」も表示する。
    ステップごとに「販売数 × 単価 × (1 − そのステップで適用されていた値引き率)」を積み上げる。
    ここでいう「そのステップで適用されていた値引き率」は§5.2のとおり**1つ前のステップの
    `recommended_rate`**（値引き提案はそのステップの販売後に決まり、次のステップから効くため。
    `services/opportunity.py`の`build_step_records`と同じ考え方）。ステップ0は値引き0%として扱う。
    単価が未設定の商品はこの行自体を表示しない（0円と表示して誤解させない）
  - **在庫の自動調整通知**（§5.7）：終了後、その回で早期完売・売れ残りが検出され
    `initial_stock`が自動調整された商品だけ、「在庫を自動調整：+25個（次回の初期在庫 75個）」
    のように表示する（減少なら`-`）。調整が起きなかった商品には何も表示しない
  - 商品カードの下に**在庫推移グラフ**（横軸=ステップ、縦軸=残り在庫数、商品ごとに色分けした
    折れ線）を1つ表示する。`/history`の値引き率推移グラフ（`RateChart`）と同じ描画方式で、
    こちらは値引き率ではなく `remaining_stock` の推移を見せる。開始前（`detail`が無い状態）は
    表示しない。進行中は現在の`visibleStep`までを描画し、他のカードと同じタイミングで
    自動更新される（新しいAPI呼び出しは追加しない。既存の`StepOut.remaining_stock`をそのまま使う）。
    系列名（凡例）は`RateChart`と同じく`detail.finals`（実行時点のスナップショット）から解決し、
    実行中に別画面で商品が削除されても他のカードと表示名がずれないようにする。
    `remaining_stock`が無い/nullのステップは「在庫が減っていない」と誤読されないようnullのまま
    描画し（線を途切れさせる）、満タン（初期在庫）にフォールバックしない
  - **学習曲線グラフ**：連続実行が完了すると、商品カードの下（在庫推移グラフのさらに下）に
    表示される。横軸=実行回（1〜N）、縦軸=実績廃棄率(%)、商品ごとに色分けした折れ線。
    連続実行を1度も行っていない間は表示しない。**`営業開始`（単発実行）を押すと消える**
    （直前の連続実行時点の条件が今表示中の条件と食い違って見えるのを防ぐため）
- **操作と結果**
  - `営業開始` → シミュレーションが自動進行（全40ステップ、1ステップ0.5秒間隔で画面更新）。
    二重開始はボタンを無効化して防ぐ
  - 終了時、結果を `SimulationResult` として保存し、`/history` から見られるようにする
  - `連続実行` → 指定回数ぶん`POST /api/simulations`を直列に呼ぶ（前の回の完了を待ってから
    次を呼ぶ。学習の継続は前の回がDBにコミットされて初めて次の事前分布に反映されるため、
    並列には呼べない）。実行中は `営業開始` ・ `連続実行` の両方を無効化し二重実行を防ぐ。
    全回終了後、**最後の1回**を通常の`営業開始`と同じアニメーション（0.5秒間隔）で再生し、
    あわせて学習曲線グラフを表示する。各回とも通常のシミュレーションと同様に
    `SimulationResult`として保存され、`/history`に1回ずつ個別に残る（連続実行専用の
    まとめレコードは作らない）。途中の回で1回でも失敗したら、そこで打ち切りエラーを表示する
    （すでに成功した回の履歴は残る。ロールバックしない）

### ② 商品設定画面 `/products`

- **目的**：商品の事前分布パラメータ（天気・曜日・イベント別の基準需要）を確認し、
  商品を追加・編集・削除する
- **表示要素**
  - 商品を一覧表示。各商品の天気×曜日×イベントの組み合わせごとの基準需要（λ値）と、
    **値引き感度**（`elasticity`。値引き10%あたり需要が何倍になるか）を表示する
    読み取り専用の一覧（12条件の個別編集はしない）。この一覧はシミュレーション実行のたびに
    変わりうる（§2「学習の継続」・§5.2 step4）。同じ条件で繰り返し実行した後にこの画面を開くと、
    α/βの値が初期値から変化しているのが確認できる
  - `商品を追加` フォーム：商品名（テキスト）・初期在庫（数値・1以上）・値引き感度（数値・
    0より大きい）・基準需要（数値・0より大きい。「平日・晴れ・イベントなしの日、1ステップに
    平均何個売れそうか」の目安値）・**単価（数値・円・任意。空欄可）**の5項目を入力する。
    単価は「わかれば入れる」項目で、シミュレーション画面の推定売上表示（§4①）にのみ使う。
    **2026-11-26追加**：さらに**種類**（セレクト。`弁当・丼`／`揚げ物の単品`／`軽食・つまみ`。
    既定は`弁当・丼`）を選ぶ。編集時も現在の種類をプリフィルする。一覧の各商品に種類を表示する
  - **入力エラーのヒント表示**（使い勝手向上のための改善。追加・編集フォーム共通）：
    `追加`/`保存`ボタンが無効化されている間、その理由を1行のヒント文でボタンの下に出す
    （例：「商品名を入力してください」「初期在庫は1以上にしてください」）。複数条件を
    満たしていない場合は、商品名→初期在庫→値引き感度→基準需要の順で**最初に引っかかった
    1件だけ**を出す（一度に全部出して圧迫しない）。すべて満たしていればヒントは出さない。
    ページレベルのAPIエラー（`.error`。赤系）とは見た目を区別する専用クラス（`.hint`。
    `--sub`色・控えめなトーン）を使い、`flex-basis:100%`でボタンの下に確実に折り返す
    （サーバーエラーと同時に出ても、どちらが致命的かユーザーが見分けられるようにする）
  - 各商品の一覧行に `編集` ボタンと `削除` ボタン
  - **在庫調整履歴**（§5.8）：`GET /api/products/{id}/stock-adjustments`が1件以上あれば、
    その商品のカード内に折れ線グラフ（横軸=発生順、縦軸=`new_initial_stock`）を小さく表示する。
    0件（まだ一度も自動調整が起きていない）の商品には何も表示しない（グラフ枠だけを空で
    出さない）。増加（`reason: "opportunity"`）と減少（`reason: "overstock"`）が交互に起きながら
    値が収束していく様子を見せるのが狙い（§5.7 step4のダンピングの効果を可視化する）
- **操作と結果**
  - `商品を追加` → 入力した基準需要から §5.4 の計算式で12条件ぶんの事前分布を自動生成し、
    商品を作成する。作成後、一覧が更新される
  - `編集` → その商品の行が追加フォームと同じ5項目の入力欄に変わる（インライン編集）。
    5項目とも**現在の値をプリフィルした状態**で開く（商品名・初期在庫・値引き感度・単価は
    そのままの値、基準需要だけは保存済みの `晴れ_平日_なし` の alpha を逆算して
    （`alpha ÷ 2.4`。§5.4 の倍率 晴れ1.2×平日1.0×イベントなし1.0×beta2.0 の逆算）表示する）。
    `晴れ_平日_なし` の条件で学習が進んでいる（シミュレーション実行でalphaが書き換わっている）
    場合、逆算元も学習後の値になる（＝編集フォームを開いた時点の「現在のモデルの理解」が
    初期値として出る。元々の基準需要そのものを復元する機能ではない）。
    `保存` を押すと、新しい基準需要で12条件ぶんの事前分布を作り直し、商品名・初期在庫・
    値引き感度・単価とあわせて上書きする。**API（PATCH）は部分更新ではなく全項目の上書き**で、
    フォームで直さなかった項目もプリフィルされた現在値をそのまま送信する
    （サーバー側は「送られなかった項目は前の値を保持する」という差分更新をしない）。
    これにより学習内容（12条件ぶんの事後分布）は編集のたびにリセットされる。
    保存に失敗した場合のエラーメッセージは、画面上部の「商品を追加」カードではなく、
    **編集中のカード自身**に表示する（使い勝手向上のための改善。エラーが操作していた
    場所から離れた位置に出て見落とされるのを防ぐため）。`編集`ボタンを押して編集を
    開始すると、トップの「商品を追加」カードに残っている古いエラー（追加・削除の失敗）も
    一緒に消える（編集という別の操作を始めたのに、今の操作と無関係なエラーが
    画面に残り続けるのを防ぐため）
  - `削除` → 確認なしで即座に削除する（このアプリはローカル単一ユーザー・デモ用途のため）。
    削除した商品が過去のシミュレーション履歴に含まれていても、履歴の表示は壊さない
    （商品名は「?」として表示される。§5.2 のとおり `Product` の行を消すだけで、
    過去の `PurchaseLog` 等は消さない）

## 5. 処理フロー

### 5.1 事前分布の設定（seedデータ）

商品ごとに、天気（晴れ/曇り/雨）×曜日（平日/休日）×イベント有無の**12通り**の組み合わせに
対して基準需要（ガンマ分布の形状パラメータ相当）をあらかじめ `seed/products.json` に持つ。

### 5.2 シミュレーション実行（`services/simulation.py`）

**入力**：天気・曜日・イベント有無・目標廃棄率

1. 選択条件に対応する事前分布（ガンマ分布のパラメータ α, β）を各商品ごとに読み込む
2. 全40ステップ（営業時間10:00〜22:00相当を圧縮。1ステップ18分）を1ステップずつ進める。各ステップで：
   a. 現在の値引き率と値引き感度から購入確率を補正し、ポアソン分布で購入個数を乱数生成
      （**乱数シードは `SimulationRun.id` から決定的に導出**し、同じ条件・同じ実行順なら
      同じ結果になるようにする）
   b. 生成した購入ログをガンマ-ポアソン共役更新の尤度として事後分布（α', β'）を更新。
      **在庫が既に0（完売済み）のステップは購入生成も更新も行わない**（**2026-08-14追加**：
      完売後は「これ以上売れたか」を観測できない打ち切りデータのため。ガードが無いと、
      完売後の残りステップぶんβ（既知の露出）だけが増え続けてα/βが実際の需要より
      大幅に低く見えてしまい、「学習の継続」でその下振れが次回の事前分布として
      持ち越されてしまう不具合があった。実際に何度もシミュレーションを重ねたときに、
      条件によっては回を追うごとに序盤の値引き提案が早まっていく形で発覚した）
   c. **実際にここまで売れた個数**が、**目標廃棄率を満たすために本来ここまでに売れているべき
      個数（時間に比例した直線的なペース）**より一定以上少なければ、その遅れを取り戻すのに
      必要な値引き率を、事後分布の平均（α/β）を使って計算する。前回提案から**5%pt以上**
      変化した場合のみ新しい提案として記録・表示する（§5.3で詳述）。**2026-08-14改訂**：
      以前はMAP推定（ガンマ分布の最頻値`(α-1)/β`）を使っていたが、`α≤1`（観測がまだ少ない
      開店直後によく起こる）だと最頻値がちょうど0に潰れてしまい、「今のペースなら一日中
      売れない」という誤判定でいきなり上限値引き（75%）が提案される不具合があったため、
      0に潰れない平均に変更した。**2026-08-15改訂**：さらに、「事後分布の平均から残り時間の
      必要ペースを毎ステップ計算し直す」という**見込みベース**の判定そのものが、実店舗の
      感覚と合わないという指摘を受けた（まだ実際に売れ残っているか確定していないのに、
      統計的な見込み計算だけで先回りして値引きを決めているように見え、信用しづらい）。
      これを受けて、判定の起点を**見込み**から**実際の遅れ**に変更した（§5.3参照）
3. 40ステップ終了時、各商品の最終在庫 ÷ 初期在庫を実績廃棄率とし、目標廃棄率以下なら達成、
   超えていれば未達とする
4. **学習の継続**：終了時点の事後分布（α, β）を、実行した条件キー（`condition_key`）に対応する
   `Product.prior_demand` の該当エントリへ書き戻す。他の11条件のエントリは変更しない。
   これにより、同じ条件で次にシミュレーションを実行すると、今回終了時点の事後分布が
   次回の事前分布（開始時のα, β）になる（§5.1 の初期値は最初の1回目にのみ使われる）。
   初期在庫0で今回スキップされた商品は書き戻しの対象外（元の事前分布のまま）

**出力**：ステップごとの `PurchaseLog` と `DiscountRecommendation`、終了時の `SimulationResult`、
更新後の `Product.prior_demand`
**エラー時**：初期在庫が0の商品は購入ログ生成をスキップする（ゼロ除算を避ける）

### 5.3 値引き提案の計算式

**2026-08-15改訂**：スーパーの惣菜売り場でアルバイトをしている視点から、「まだ実際に
売れ残っているか確定していないのに、統計的な見込み計算だけで先回りして値引きを決めている
ように見え、信用しづらい」という指摘を受けた。これを受けて、**値引きが必要かどうかの
「判定」は実際の販売実績（打ち切りの無い事実）で行い、必要と判定された場合の「値引き幅」
の計算だけに事後分布の平均（統計的な見込み）を使う**、という役割分担に変更した。

#### トリガー：見込みではなく実際の遅れで判定する

```
実際に売れた個数 < 目標ペースで売れているべき個数 − 許容マージン
```
を満たした場合だけ、値引き幅の計算（次項）に進む。満たさなければ値引き率は0%のまま
（または直前の値引き率を維持。単調増加ルールは変わらない）。

- **目標ペースで売れているべき個数**（直線ペース） =
  `(初期在庫 − 目標廃棄率 × 初期在庫) × (経過ステップ数 ÷ 40)`。目標廃棄率を満たすために
  必要な販売数を、開店から閉店まで一定のペースで売っていくと仮定した、時間に比例する目安値
- **実際に売れた個数** = `初期在庫 − 現在庫`。事後分布ではなく、その回で実際に生成された
  購入ログをそのまま数えた事実
- **許容マージン** = 初期在庫の15%（`SHORTFALL_MARGIN_RATE = 0.15`。`services/simulation.py`）。
  数ステップぶんの偶然の売れ行きのブレでは反応しないための遊び。開店直後は「目標ペースで
  売れているべき個数」自体が小さい（例：ステップ5時点では目標の12.5%ぶんしか無い）ため、
  このマージンだけで序盤の過敏な反応は自然に抑えられる。**以前（2026-08-14）導入していた
  「開店直後5ステップは値引き提案を計算しない」という`GRACE_PERIOD_STEPS`の仕組みは、
  この直線ペースとの比較に役割を吸収されたため削除した**（同じ目的を2つの仕組みで
  二重に持たない）

#### 値引き幅：遅れを取り戻すのに必要な値引き率（計算式自体は変更なし）

```
必要値引き率 = f(事後分布の平均需要率, 残りステップ数, 目標廃棄率, 商品の値引き感度)
```

上のトリガー条件を満たした場合だけ、事後分布の平均需要率（α/β）を残りステップ数に掛けた
「このまま何もしなければ残り時間で自然に売れる見込み数」と、「残り時間で目標廃棄率以内に
売り切れる見込み数」を比べ、不足分を値引き感度で割り戻した値引き率を計算する（連続値）。
この計算式自体（`_required_discount_rate`）は2026-08-14のMAP→平均への変更のまま変えていない。
**2026-11-26修正**：不足分を値引き率に割り戻す部分は、需要倍率の式（下の「値引き感度」。2026-08-15に
1乗→2乗へ改訂）の逆算になっていなければならないが、1乗の式（`(必要倍率−1)×10%÷感度`）のまま
残っていて、必要な値引き幅を大きめに見積もっていた。2乗の式の逆算
`値引き率 = 10% × √((必要倍率−1) ÷ 感度)`に直した（例：必要倍率2.0・感度0.15で、旧式は約67%、
新式は約26%）。seedの12商品・20通りの乱数で比べると、平均廃棄率は晴れ・平日で動的16.0%／固定25.5%、
雨・平日で動的33.4%／固定45.2%（修正後も動的値引きの方が少ない）
「いつ値引きを検討し始めるか」だけを実績ベースに変え、「検討に入った後どれだけ値引きするか」
は引き続き統計的な見込みで決める

- **値引きの刻み（実店舗の制約の再現）**：実店舗の値引きシールは`30%引き`・`半額（50%引き）`・
  `75%引き`の3段階しか無い、というこのアプリの企画の出発点（§1）に合わせ、上で計算した連続値は
  そのまま使わず、**`0% / 30% / 50% / 75%`のいずれか**に丸めてから提案・適用する
  （`DISCOUNT_TIERS = (0.0, 0.30, 0.50, 0.75)`）。丸め方は**切り上げ**（連続値以上で最小の刻みを選ぶ）。
  目標廃棄率を満たすための値引きが刻みの間の半端な値になった場合に、切り下げて目標未達になるより
  安全側（売り切りやすい側）に倒すため。連続値が75%を超えていたら75%に丸める（最大値引き）
- 値引き率が取りうる値は`0% / 30% / 50% / 75%`の4通りだけになる（`services/simulation.py`の
  `MAX_DISCOUNT`は`0.75`）
- **2026-11-26改訂（作り直し第1弾の2）：ズバリ引き**。実際の売り場では、21時に売れ残っている惣菜は
  「〇〇円」と値段を直接決めて貼る（ズバリ引き）。これに合わせて刻みを時刻で分ける：
  - **21時より前**（`step < ZUBARI_START_STEP`）は`0% / 30% / 半額`の3段階だけ。必要な連続値が
    半額を超えても半額に抑える（`PRE_ZUBARI_TIERS`）
  - **21時を過ぎたステップ以降**（`ZUBARI_START_STEP = 37`＝21:06。1ステップ18分のため21:00ちょうどの
    ステップは無い）は、半額より下を**5%ずつ**の刻み`55% / 60% / 65% / 70% / 75%`も使える
    （`ZUBARI_TIERS`）。下限は**元の値段の75%引き**（`MAX_DISCOUNT`は`0.75`のまま）
  - 値引き率が取りうる値の全体は`DISCOUNT_TIERS = (0, 0.30, 0.50, 0.55, 0.60, 0.65, 0.70, 0.75)`
  - 画面では、半額より大きい値引きを**10円単位の値段**で表示する（例：430円の55%引き→
    193.5円→切り下げて`ズバリ ¥190`）。ただし下限（75%引きの値段）を10円単位に切り上げた値より
    下げない（`frontend/src/lib/discountLabel.ts`）。単価が無い商品は`ズバリ引き（60%引き）`のように
    率で表示する。推定売上は値引き率で計算する（表示の10円丸めは反映しない）
  - 「前回から5%pt以上変わったら新しい提案」の判定は、浮動小数点の誤差（0.60−0.55＝0.0499…）で
    見落とさないよう、差を小数第6位で丸めてから比べる
  - 「一度上げたら下げない」は、シールをやめてモニター表示にしても**お客さんの信頼のためのルール**
    として残す
- **2026-11-26追加：段階を飛ばさない**。ブラウザで確認したところ、18時台にいきなり半額になる商品が多く、
  実際の売り場の「30%引き → 半額」の流れと合わなかった。半額までは**値引きなし → 30%引き → 半額を
  1段ずつ**上げ、**30%引きは最低3ステップ（54分。`MIN_STEPS_AT_30`）続ける**。半額からズバリ引き
  （21時以降）は残り時間が少ないので、必要な刻みまで一度に上げてよい。seedの12商品・20通りの乱数で、
  30%引きの開始は中央18:24、半額は中央19:18。平均廃棄率は晴れ・平日で動的19.5%／固定19.9%／
  固定＋お客さんが待つ23.3%、雨・平日で40.4%／41.0%／45.5%（**「お客さんが待つ」効果を入れない
  限り、動的値引きと固定スケジュールの差はほとんど無い**）
- **値引きは下げない（一方向）**：値引きシール（実店舗）は一度貼ったら剥がせない、という
  物理的な制約を再現するため、**その回の値引き率は一度上がったら二度と下がらない**
  （同じ刻みのままか、より大きい刻みに上がるかのどちらかだけ）。ステップごとに再計算した
  刻みが直前の値引き率より低くても、直前の値引き率をそのまま維持する（切り下げない）。
  これにより一回の営業（1シミュレーション）の中で値引き率は単調増加になる

#### 値引き感度（elasticity）：大きい値引きほど急激に効く非線形な式に変更（2026-08-15改訂）

```
需要倍率 = 1 + 値引き感度 × (値引き率 ÷ 10%)²
```

以前は`(値引き率 ÷ 10%)`の1乗（値引き率に比例）だったが、「半額になった瞬間に速攻売れる」
という実店舗の感覚（特に寿司のような鮮度が命の商品）に対し、比例の式では効きが弱すぎる
という指摘を受けて2乗に変更した。小さい値引き（30%）は以前よりやや強めに効く程度に留まり、
大きい値引き（50%・75%）になるほど需要倍率が急激に跳ね上がる。既存の値引き感度の値
（唐揚げ`0.12`・おでん`0.10`・寿司`0.18`。相対的な大小関係は寿司が最も値引きに敏感、という
現実の並びとして妥当なためそのまま流用）で比較すると：

| 値引き率 | 唐揚げ(0.12) | おでん(0.10) | 寿司(0.18) |
|---|---|---|---|
| 30%引き | 2.08倍 | 1.90倍 | 2.62倍 |
| 半額 | 4.00倍 | 3.50倍 | 5.50倍 |
| 75%引き | 7.75倍 | 6.63倍 | 11.13倍 |

（以前の比例式ではそれぞれ最大でも唐揚げ1.9倍・おでん1.75倍・寿司2.35倍程度だった。
寿司が半額で5.5倍・75%引きで11倍という急激な伸びは「速攻売れる」実感に近い）

**2026-11-26**：seedの商品を§2.1の12件に入れ替えた。この表の3商品は改訂当時の記録として残す。
新しいseedでは種類ごとに弁当・丼0.18／軽食・つまみ0.14／揚げ物の単品0.06を使う
（半額で弁当・丼は6.5倍、軽食・つまみは4.5倍、揚げ物の単品は2.5倍）

### 5.11 ナイトマネージャーの承認とモニター表示（2026-11-26追加。作り直し第1弾の3）

実際の売り場では、値引きを決めて貼るのはナイトマネージャー（NM）で、NMが1人の日は全部を1人で回す。
最終的にはシールをやめて売り場のモニターに値引きを出すが、**値段まで決めるズバリ引きは、取り返しが
つかない（一度出した値引きは下げない）ため、NMの確認を必ず通す**。30%引き・半額は今も時刻で決まっている
値引きなので自動で出す（1ステップ18分のため「10分たったら自動」は実質「次のステップで反映」と同じ）。

第1弾では、NMの承認を**シミュレーション条件として再現する**（画面で本当に押せる対話型は第2弾）：

- **入力**：`approval_delay_steps`（0〜3。ズバリ引きの提案から何ステップ後にNMが承認するか。
  0＝すぐ、1＝18分後、2＝36分後、3＝54分後）
- **処理**（`services/simulation.py`の`run_simulation`）：
  1. 提案（`recommended_rate`）の決め方は今までどおり（§5.2・§5.3）
  2. 提案が30%引き・半額（`HALF_PRICE_RATE`＝0.50以下）なら、そのままモニターに出す（`applied_rate`）
  3. 提案がズバリ引き（半額より大きい）なら承認待ちにし、提案したステップ＋`approval_delay_steps`の
     ステップで承認されてモニターに出る。承認待ちの間に新しいズバリ引きが提案されたら、承認待ちを
     その提案に置き換える（その提案のステップから数え直す）
  4. **実際の購入に効くのはモニターに出ている値引き（`applied_rate`）**。推定売上（`lib/revenue.ts`）も
     `applied_rate`で計算する
  5. `approval_delay_steps = 0`なら、`applied_rate`は常に`recommended_rate`と同じ（以前と同じ動き）
- **出力**：各ステップの`applied_rate`（`recommended_rate`と同じく「次のステップから使う値」）。
  `PurchaseLog.applied_rate`に保存し、`GET /api/simulations/{id}`の履歴の再構築でも返す。
  `SimulationRun.approval_delay_steps`も保存して一覧・詳細で返す。`POST /api/compare`も同じ
  `approval_delay_steps`を受け取り、動的値引き側の`dynamic_steps[].recommended_rate`には
  **モニターに出ていた値引き（`applied_rate`）**を返す
- **画面**：商品カードの大きな値引き表示とモニター（§4①）は`applied_rate`を表示する。
  `applied_rate < recommended_rate`の間は、カードに`承認待ち：ズバリ ¥190（ナイトマネージャーが承認すると
  モニターに出ます）`を出す
- **目安**（seedの12商品・20通りの乱数の平均廃棄率。承認の遅れ0／1／2／3ステップ）：晴れ・平日
  16.0%／16.3%／16.6%／16.6%、雨・平日 33.4%／33.8%／34.3%／34.3%。ズバリ引きは21時過ぎの
  最後の3ステップだけなので差は小さいが、NMが忙しいほど廃棄が増える

### 5.12 1日の売れ方と16時の補充（2026-11-26追加）

ブラウザで確認したところ、ほぼ全商品が12〜14時に値引きを始めていた（カツ丼が13時に半額など）。原因は
「1日中同じペースで売れる」前提と、時間に比例した目標ペースで「遅れている」と判断していたこと。
売り場の聞き取り：**朝の分を昼（12時が一番の山）に定価で売る → 16時ごろ補充 → 昼の売れ残りは
「昼に買った人が夜の分も買う」ため補充分と一緒に残りがち → 昼に値引きは絶対に無い → 17時は12時より
少ないが定価で売れる → 18時は「19時に値引きがある」と分かっているのであまり買われない → 19時の30%引きで
少し売れるが「あと1時間で半額」と待つ人が多い**。

1. **1日の売れ方（`demand_curve`）**：時間帯ごとの需要の重み（10時0.6／11時1.2／12時2.0／13〜16時0.6／
   16時0.9／17時1.4／18時1.2／19〜22時0.8。1ステップあたり平均1.0に正規化）。購入の生成は
   `事後分布の平均 × 時間帯の重み × 値引きの需要倍率`。ベイズ更新は**時間帯の重みも値引きと同じ
   「既知の露出」として扱う**（`alpha += 個数`、`beta += 時間帯の重み × 需要倍率`）。露出が変わっても
   ガンマ-ポアソン共役のままなので、中心の逐次ベイズ更新の仕組みは変わらない
2. **16時の補充**：1日の在庫（`Product.initial_stock`）を朝の分と補充分に分ける（`split_stock`。朝の分は
   切り上げ。**実際の割合は分からないため、いったん半分ずつ**）。ステップ20（16:00）の販売の前に
   補充分を並べる。補充までは朝の分しか売れない（昼に売り切れることもある）。各ステップの
   `remaining_stock`と実績廃棄率は「1日の残り（店頭在庫＋まだ補充していない分）」で数える
   （履歴の再構築〔初期在庫−累計販売数〕・機会損失・過剰在庫の判定と同じ数え方）
3. **値引きの判断は18時から、夜の分で見る**：
   - 判断を始めるのは`EARLIEST_DISCOUNT_STEP = 27`（18:06）。昼に値引きは無く、17時台の夕方の山も
     定価で売れるため。夜の在庫は1商品あたり十数個と少なく、これが無いと1〜2個の偶然の遅れで17時台に
     値引きしてしまっていた
   - 「遅れているか」（§5.3のトリガー）は、**16時の補充直後の在庫（昼の売れ残り＋補充分）**を基準に、
     夜の売れ方（補充以降の`demand_curve`の累積割合）に沿って売れているかで見る（朝からの1日全体で
     見ると、昼の売れ残りがあるだけで補充直後に値引きしてしまっていた）
   - 値引き幅の計算（§5.3）の「残り時間」は、残りステップの需要の重みの合計を使う
4. **seedの需要の合わせ直し**：晴れ・平日・イベントなしで、1日の定価の需要＝作った量になるよう、
   基準需要を`初期在庫 ÷ (40 × 1.2)`にした（以前は約84%しか売れない設定で、晴れでも毎日余る前提に
   なっていた）
5. **「お客さんが待つ」効果（比較画面だけ。仮定）**：値引きの時刻が毎日同じだと、お客さんがそれを覚えて
   待つ。`POST /api/compare`の`customer_anticipation`（既定false）をtrueにすると、**固定スケジュール側だけ**
   18時台（ステップ27〜29）の需要を0.5倍、30%引きの間（ステップ30〜34）を0.6倍にする。お客さんの行動の
   変化なので、店側の学習（ベイズ更新の露出）には入れず、購入の生成にだけ掛ける。動的値引きは日によって
   時刻が変わるので掛けない（ここは仮定であり、画面でも「仮定」と明記して切り替えられるようにする）

**目安**（seedの12商品・20通りの乱数の平均。値引き開始は動的値引きの最初の値引きの時刻）：

| 条件 | 値引き開始（中央） | 廃棄：動的 | 固定 | 固定＋お客さんが待つ |
|---|---|---|---|---|
| 晴れ・平日 | 18:24 | 18.1% | 19.9% | 23.3% |
| 曇り・平日 | 18:24 | 24.3% | 25.8% | 30.5% |
| 雨・平日 | 18:24 | 38.8% | 41.0% | 45.5% |
| 晴れ・休日 | 18:24 | 11.7% | 13.3% | 15.5% |

（雨の日はどちらも廃棄が多い。値引きだけでは取り返せない「作る量の見込みのずれ」で、§5.7の在庫の
自動調整と、作り直し第1弾の4〔長期休み〕・第2弾の課題）

### 5.13 長期休みの条件（2026-11-26追加。作り直し第1弾の4）

学習の継続（§5.2 step4）は「昨日までの売れ方」を次の予測に使うため、状況が急に変わる日に弱い。
例：学生の多い町で学生が帰省すると客が減るのに、ふだんの日の学習で作りすぎる（本人の指摘）。
大学の休み・帰省の期間は前もって分かるので、**システムには分からない地域の事情を、人がカレンダーを見て
入れる**。

- **条件**：天気×曜日×イベント有無に「長期休み」（`is_long_vacation`）を足し、事前分布を**24条件**で持つ
  （`services/prior.py`の`generate_prior_demand`）。長期休みの日の需要の倍率は**0.7**（仮の値）
- **キー**：ふだんの日は以前と同じ`晴れ_平日_なし`、長期休みの日は末尾に`_長期休み`を付けた
  `晴れ_平日_なし_長期休み`（`condition_key`／`frontend/src/lib/conditionKey.ts`）。ふだんの日のキーの
  形式を変えないので、既存の機能（商品編集の基準需要の逆算など）はそのまま使える
- **学習の分離**：長期休みの日の結果は`_長期休み`のキーにだけ書き戻す。帰省で客が減った日の学習が、
  ふだんの日の予測に混ざらない（逆も同じ）
- **入力**：`POST /api/simulations`・`POST /api/compare`の`is_long_vacation`（既定false）。
  `SimulationRun.is_long_vacation`に保存し、一覧・詳細で返す。シミュレーション画面・比較画面に
  `長期休み`のチェックボックス、履歴の条件に`/ 長期休み`を表示する
- **今回やらないこと**：値引きタイミングの傾向分析（§5.10）の12マスは天気×曜日×イベントのまま
  （長期休みの日も同じマスに数える）。履歴の条件フィルタ・CSVにも長期休みの列は足さない
- **限界**：このシミュレーションは、購入を「店側が今信じている需要（事後分布の平均）」から生成している。
  そのため「長期休みを入れ忘れたら、どれだけ作りすぎるか」は、今の仕組みでは数字で示せない
  （本当の需要と店側の予測を分けて持つ必要がある。第2弾の課題）

### 5.14 本当の需要と店側の予測を分ける（2026-11-26追加）

ブラウザで確認中、カツ丼の作る量が回を追うごとに4個まで減り、廃棄率が83%になっていた。調べると、
**購入を店側の予測（事後分布の平均）から作っていたため、正しい答え（本当の需要）がどこにも無かった**。
予測がたまたま下がると翌日の客も減ってまた下がる…と、予測が0に向かって流れていた（たこ焼きは10日で
平均需要0.374→0.004）。さらに、在庫が足りず欲しい数だけ売れなかったステップの「売れた数（在庫で頭打ち）」
をそのまま需要として学んでいたため、下に偏っていた。

1. **本当の需要**：商品ごとに条件別の「お客さんの本当の需要」（1ステップあたりの平均）を持つ
   （`Product.true_demand`。seedと商品の追加・編集では、事前分布と同じ倍率表から作る＝最初の予測は
   本当の需要と同じ平均から始まる）。**購入はここから作り**、時間帯の重み・値引きの需要倍率・
   （比較画面の）お客さんが待つ効果を掛ける。学習の継続では書き換わらない
2. **店側の予測**：事前分布 → 購入のたびにベイズ更新 → 事後分布（中心の逐次ベイズ更新。変えない）。
   値引きの判断・幅の計算に使い、終わった時点の事後分布を次回の事前分布にする
3. **売り切れたステップの学習**（`_learn`）：欲しい数より在庫が少なかったステップは、本当に欲しかった数が
   分からない打ち切りデータ。捨てると「需要が少なかったステップ」だけを学ぶ偏りが出るため、
   **「売り切れるまでの間だけ売っていた」とみなし、露出を「売れた数 ÷ 予測の平均」に縮めて**学ぶ
   （このステップの露出は超えない）
4. 固定スケジュール比較も同じ本当の需要・同じ乱数から購入を作る（店側の予測は固定側の値引きには使わない）

**確認**（seedの12商品・晴れ・平日・学習の継続と在庫の自動調整を重ねる）：10日後の予測は本当の需要の
0.91〜1.07倍。最初の予測をわざと半分にしても、10日で0.91〜1.07倍、30日で0.93〜1.04倍に戻る。

**比較の結果**（20通りの乱数の平均。廃棄率・推定売上）：

| 条件 | 動的値引き | 固定スケジュール | 固定＋お客さんが待つ |
|---|---|---|---|
| 晴れ・平日 | 2.7%・¥57,589 | 0.5%・¥57,815 | 1.0%・¥55,267 |
| 曇り・平日 | 4.6%・¥52,876 | 1.9%・¥54,149 | 3.7%・¥51,221 |
| 雨・平日 | 10.8%・¥42,816 | 11.7%・¥43,797 | 16.6%・¥40,253 |
| 晴れ・休日 | 0.8%・¥61,562 | 0.0%・¥61,082 | 0.1%・¥59,481 |

**「お客さんが待つ」効果（仮定）を入れない限り、今の動的値引きは固定スケジュールとほぼ同じか少し負ける**。
動的値引きは目標廃棄率（5%）以内に収まれば値引きを控えるため、晴れの日は固定より廃棄が多く、売上も
ほぼ同じ。動的値引きの判断（いつ・どれだけ値引きするか）の改善は次の課題。

**原因の分析（2026-11-26）**：目標廃棄率を0%・3%・5%・10%と変えても、動的値引きの売上は固定時刻に
届かなかった（晴れ・平日で−226〜−591円、雨・平日で−951〜−1,110円）。
- 雨の日：動的値引きは固定時刻より早く値引きする（30%引き18:24・半額19:18）ので廃棄は少ないが、
  定価で買うはずだったお客さんにも値引きしてしまい、売上が減る
- 晴れの日：早めに30%引きにする一方、目標廃棄率以内なら21時以降のズバリ引きで売り切ろうとしないため、
  廃棄が多く売上も少ない。固定時刻は遅めに値引きし、最後は必ずズバリ引きで売り切る
- 根本は、**今の判断が「目標の廃棄率に収まるか」だけを見ていて、売上を考えていない**こと。
  改善の方向は「値引きしたとき・しないときの閉店までの売上の見込み（事後分布を使う）を比べて決める」。
  値引きの判断の考え方そのものを変えるため、本人と相談してから進める

### 5.15 古いデータを少しずつ忘れる（2026-11-26追加。状況の変化への対策B）

学習の継続（§5.2 step4）で営業の終わりの事後分布を次の日の事前分布にするとき、alpha・betaの両方に
`FORGETTING_FACTOR = 0.9`を掛ける（`carry_over`）。平均（予測そのもの）は変わらず、確信の強さだけが
毎日1割ずつ弱まる＝おおよそ直近10日分を重く見る。客層の変化のような**ゆっくりした変化**に早く追いつくため。
前もって分かる変化は長期休みの条件（§5.13。対策A）、当日の変化は「いつもと違う」の通知（§5.16。対策C）で扱う。
テストでは、本当の需要が15日目から1.0→0.6に下がったとき、忘れる方が5日後の予測が0.6に近いことを確認している。

### 5.16 「いつもと違う」の知らせと、実際の状況（2026-11-26追加。状況の変化への対策C）

本当の需要と店側の予測を分けた（§5.14）ので、「店が入れた条件」と「実際の状況」を分けて試せるようになった。

- **実際の状況**（`actual_situation`。シミュレーション用。店は知らない）：`いつもどおり`／`実は長期休み`
  （店は長期休みを入れ忘れた）／`実は近くでイベント`（店は知らなかった）。**お客さんの本当の需要だけ**が
  この状況を重ねた条件で決まり、店の予測・値引きの判断・学習の書き戻し先は、店が入れた条件のまま。
  `POST /api/simulations`・`POST /api/compare`で受け取り、`SimulationRun.actual_situation`に保存する
- **知らせ**：昼の山が終わった13:00（`ALERT_STEP = 10`）に、開店からの販売数を、その日の店の予測
  （事前分布の平均×時間帯の重み。朝の分を上限）と比べる。0.75倍未満なら`low`、1.3倍を超えたら`high`
  （予測が3個未満の商品は判定しない）。各ステップの`alert`として返す（POSTの応答だけ。履歴の再構築では返さない）
- **店全体の知らせ**：商品1つずつの知らせは、いつもどおりの日でも2割ほどの商品に出てばらつきが大きいため、
  画面には**半分以上の商品が同じ向きに外れたときだけ**「今日はいつもより売れていません（12商品中8商品）。
  長期休みなど、入れ忘れた条件がないか確認してください。」と出す（`frontend/src/lib/storeAlert.ts`）

**確認**（seedの12商品・晴れ・平日・30通りの乱数）：

| 状況 | 廃棄 | 商品ごとの「売れていない」 | 店全体の知らせが出た日 |
|---|---|---|---|
| いつもどおり | 2.6% | 20%の商品 | 3% |
| 長期休みを正しく入れた | 6.4% | 24%の商品 | 3% |
| 長期休みを入れ忘れた | 6.4% | 52%の商品 | 73% |

（上の表は基準0.7倍のとき。長期休みの需要0.7倍がちょうど境目になっていたため、基準を**0.75倍**に変えた。
60通りの乱数で、店全体の知らせが出た日は：基準0.7倍＝誤報3%・入れ忘れの検出73%／0.75倍＝誤報7%・検出87%／
0.8倍＝誤報20%・検出95%／0.85倍＝誤報32%・検出98%。誤報が多いと知らせが無視されるため、0.75倍にした）

**限界**：入れ忘れても、その日の廃棄は変わらない。今の仕組みでは**作る量（`initial_stock`）が条件の予測と
関係なく決まっている**ため。入れ忘れの害は、その日の学習がふだんの日のキーに書き戻され、ふだんの予測に
混ざること。条件の予測から翌日の作る量を決める仕組み（作り直しの整理の第3段階）は次の課題。

### 5.17 作る量を予測から決める（2026-11-26追加。作り直しの整理の第3段階の一部）

§5.16の限界（作る量が条件の予測と関係なく決まるので、長期休みを入れても入れ忘れても廃棄が変わらない）への対策。

- `stock_mode`（`いつもの量`／`予測から決める`。既定はいつもの量）。`予測から決める`の日は、各商品の作る量を
  **その日の条件の予測（事前分布の平均）× 1日の時間帯の重みの合計**（＝定価で1日に売れる見込み）の四捨五入
  （最低1個。`planned_stock`）にする。`SimulationResult.initial_stock`にはこの量を残す
- `予測から決める`の日は、作る量を予測で決めているので、いつもの量の自動調整（§5.7）はしない
- 画面：売り場の「お店の決めごと」に`作る量`のセレクト

**確認**（seedの12商品・晴れ・平日・実際は長期休み・30通りの乱数）：

| 作る量・状況 | 作った量 | 廃棄 | 売上 |
|---|---|---|---|
| 予測から決める・長期休みを正しく入れた | 186個 | 4.2個（2.2%） | ¥39,758 |
| 予測から決める・長期休みを入れ忘れた | 265個 | 16.9個（6.4%） | ¥48,478 |

長期休みを正しく入れると作る量が減り、廃棄が約4分の1になる（人が入れる情報が効く）。一方で売上は下がる。
**このシミュレーションには原価（作るのにかかるお金）が無い**ため、多く作って値引きで売り切る方が売上だけは
高く見える。本当に得かは原価を入れた利益で比べる必要がある（原価の値が分からないので推測では入れない。次の課題）。

### 5.4 商品追加時の事前分布の自動生成（`services/prior.py`）

**入力**：基準需要（`base_demand`。平日・晴れ・イベントなしの日の1ステップあたり平均需要）

天気・曜日・イベント有無の全12通りの組み合わせについて、`seed/products.json` を作った ときと
同じ倍率テーブルを使い、`alpha = base_demand × 天気倍率 × 曜日倍率 × イベント倍率 × beta`、
`beta = 2.0`（固定）として各条件のガンマ分布パラメータを計算する。

| 区分 | 倍率 |
|---|---|
| 天気：晴れ | 1.2 |
| 天気：曇り | 1.0 |
| 天気：雨 | 0.7 |
| 曜日：平日 | 1.0 |
| 曜日：休日 | 1.3 |
| イベント：なし | 1.0 |
| イベント：あり | 1.4 |

**出力**：`condition_key()`（§5.2 と同じ形式）をキーにした12エントリの辞書（**2026-11-26：長期休みを足して24エントリ。§5.13**）
**エラー時**：`base_demand <= 0` は呼び出し元（API）でバリデーションエラーとして弾き、
この関数自体はガードしない（純関数として「正しい入力なら常に正しい出力」に留める）

### 5.5 機会損失の検出と推奨追加在庫数（`services/opportunity.py`）

**入力**：`SimulationRun`（`status="finished"`のもの全件）ごとの、商品別の
`PurchaseLog`（ステップごとの`quantity`）と`DiscountRecommendation`（値引き率）

**処理**（1つの `run × product` の組ごとに判定する純関数）

1. ステップ0から順に見て、**一度でも `recommended_rate > 0` になった時点で対象外**にする
   （値引きが1回でもあれば「値引きなしで完売」ではない）
2. 値引きが一度も無いまま、**残り在庫が0になったステップ（`sellout_step`）** を探す。
   最後まで（40ステップ目まで）売り切らなければ対象外
3. `sellout_step` が **37以下**（＝閉店の3ステップ以上前）のときだけ「早期完売」として扱う
   （終了間際の完売は正常な在庫量と見なし、対象に含めない）
4. 早期完売と判定された場合、`sellout_step` までの平均販売ペースを40ステップぶんに
   引き延ばして、必要だったと見積もられる在庫数との差分を計算する：

```
steps_to_sellout = sellout_step + 1
推奨追加在庫数 = round(初期在庫 × (40 - steps_to_sellout) / steps_to_sellout)
```

**集計**：商品ごとに、該当した `run` 全件から「該当回数」「平均完売ステップ」
「推奨追加在庫数の平均」を求め、**推奨追加在庫数の平均が大きい順に上位10件**を返す
（該当0件の商品は結果に含めない）

**出力**：`{product_id, product_name, occurrence_count, avg_sellout_step, avg_suggested_increase}` の配列
**エラー時**：完了済みの `SimulationRun` が1件も無ければ空配列を返す（エラーにしない）

### 5.6 過剰在庫の検出と推奨削減在庫数（`services/overstock.py`）

`services/opportunity.py`（§5.5）の鏡像。新しいテーブルは追加せず、同じ
`PurchaseLog`／`DiscountRecommendation`／`Product`を使う。

**入力**：`SimulationRun`（`status="finished"`のもの全件）ごとの、商品別の
`DiscountRecommendation.recommended_rate`の一覧と`PurchaseLog.quantity`の合計

**処理**（1つの `run × product` の組ごとに判定する純関数）

1. その回でその商品に一度でも**最大値引き率（75%）**が提案されたかを見る
   （`services/simulation.py`の`MAX_DISCOUNT`と同じ`0.75`。§5.3参照）。一度も無ければ対象外
   （＝値引きを目一杯効かせてもいないのに余ったのは、在庫過多ではなく別の理由と見なす）
2. 最大値引きに達していても、終了時点（40ステップ目）で**在庫が0（完売）なら対象外**
   （値引きが効いて売り切れたということなので、在庫は適正だった）
3. 上記どちらも満たした場合だけ「過剰在庫」として扱う。終了時点の残り在庫数をそのまま
   推奨削減在庫数とする（機会損失側のような延長計算はしない。実際に売れ残った数そのものが
   「今回は要らなかった数」であるため）：

```
推奨削減在庫数 = 終了時点の残り在庫数（= 初期在庫 − 累計販売数）
```

**集計**：商品ごとに、該当した `run` 全件から「該当回数」「平均売れ残り数」
「推奨削減在庫数の平均」を求め、**推奨削減在庫数の平均が大きい順に上位10件**を返す
（該当0件の商品は結果に含めない）

**出力**：`{product_id, product_name, occurrence_count, avg_final_remaining, avg_suggested_decrease}` の配列
**エラー時**：完了済みの `SimulationRun` が1件も無ければ空配列を返す（エラーにしない）

### 5.7 在庫の自動調整（`services/stock_adjustment.py`）

早期完売（機会損失）・売れ残り（過剰在庫）が`/opportunities`・`/overstock`を人が見て手で
`initial_stock`を直すのを待たず、**シミュレーション終了のたびにその場で自動反映する**。
`/opportunities`・`/overstock`（§5.5・§5.6）は削除しない。過去の履歴全体を俯瞰する
読み物として引き続き使う（この節は「今回1回ぶんの結果」だけを見て即座に動く別の仕組み）。

**方向の決め方**：「売れ残ったら次回は早めに値引きを始める」ではなく「在庫の数そのものを
増減させる」を採用した。目標廃棄率はシミュレーションのたびにユーザーが選ぶ値でありPer商品の
学習対象ではないため、値引き開始時点を商品ごとに学習させる仕組みは今の設計に無い。
一方`initial_stock`はすでに`/opportunities`・`/overstock`の両方が「+n個」「-n個」という
形で提案を出しており、その数値をそのまま使える（既存インフラの再利用）

**入力**：シミュレーション終了直後（DB保存前）の、その回の商品ごとのステップ列
（`PurchaseLog`相当の`(step, quantity)`と、値引きが変化した`(step, recommended_rate)`）

**処理**（1商品ぶん。純関数）

1. §5.5の`detect_opportunity`・§5.6の`detect_overstock`を**その回の結果だけ**に対して呼ぶ
   （履歴全体の集計ではなく、今回1回ぶんのみ。両者の判定条件は両立しないため、
   該当してもどちらか一方だけになる）
2. 機会損失に該当：`推奨追加在庫数`の**半分**（四捨五入。§5.3と同じ半数切り上げではなく
   Pythonの`round()`で良い。ここは丸め方向にシビアな意味は無いため）だけ`initial_stock`に足す。
   半分が0になる場合でも、該当した以上は最低1個は増やす
3. 過剰在庫に該当：`推奨削減在庫数`の半分だけ`initial_stock`から引く。ただし**1を下回らない**
   （0にすると次回そのままではシミュレーション対象から外れてしまうため。§5.2の
   `initial_stock > 0`フィルタ）。半分が0になる場合でも、該当した以上は最低1個は減らす
   （下限1に当たって実際の減少幅がそれより小さくなることはある）
4. **提案の半分だけを反映する理由（ダンピング）**：機会損失側の推奨追加在庫数は、
   早期完売までの平均販売ペースを40ステップぶんに引き延ばす計算（§5.5）のため、
   完売が早いほど非常に大きな値になりうる（在庫を一度に倍増させかねない）。1回の結果を
   そのまま全部反映すると次回は逆に売れ残り、また逆方向に大きく振れる…という往復が
   起きやすいため、半分だけ動かして複数回の実行で徐々に収束させる
   （「連続実行」§4①と組み合わせると、収束していく様子が見られる）

**出力**：調整後の`Product.initial_stock`（該当した商品だけ更新。該当しなければ変更なし）。
`POST /api/simulations`のレスポンスに、調整が発生した商品ぶんだけ
`{product_id, product_name, delta, new_initial_stock}`の配列（`stock_adjustments`）を含める
（`delta`は正なら増加・負なら減少）。`GET /api/simulations`・`GET /api/simulations/{id}`
（履歴の一覧・再取得）では常に空配列を返す（この配列自体は`SimulationRun`に紐づけて
保存し直さない、その場限りの通知のため）。ただし調整が発生したという事実そのものは
`StockAdjustmentLog`として別に永続化し、商品ごとの調整履歴を後から追える（§5.8）
**エラー時**：どちらにも該当しなければ、その商品は`initial_stock`を変更しない

### 5.8 在庫調整履歴（`StockAdjustmentLog`）

§5.7の自動調整は`POST /api/simulations`のレスポンスでその場限りに通知されるだけで、
それまでは「今initial_stockがいくつか」しか分からず、**どう変わってきたか**は追えなかった。
在庫が完売と売れ残りを繰り返しながら適正値へ収束していく様子（§5.7 step4のダンピングの狙い）
を後から確認できるように、調整が発生するたびに1行のログとして残す。

**入力**：§5.7の処理で`compute_stock_adjustment`が`None`以外を返した時点の
`(product_id, run_id, reason, delta, new_initial_stock)`。`reason`は
`opportunity`（機会損失＝在庫を増やした）／`overstock`（過剰在庫＝在庫を減らした）のいずれか
（§5.7 step1で判定条件が両立しないため、どちらか一方に必ず定まる）

**処理**：`compute_stock_adjustment`が該当した商品ぶんだけ、`SimulationResult`と同じ
タイミング（`run.status = "finished"`にする直前の同一トランザクション）で
`StockAdjustmentLog`を1行追加する。該当しなかった商品は行を作らない

**出力**：`GET /api/products/{id}/stock-adjustments` — その商品の調整ログを`created_at`昇順
（同一`created_at`は`id`昇順でタイブレークする。「連続実行」§4①のようにPOSTを間隔を空けず
繰り返すと、環境によっては`datetime.now()`の分解能の都合で同一runの複数件が同じ`created_at`に
なりうるため）＝発生順で返す。商品が存在しなければ404。ログが0件（一度も自動調整が発生していない）
でも200と空配列を返す（エラーにしない）
**エラー時**：商品が存在しなければ404。ログが0件は正常系（上記の通り空配列）

### 5.9 固定スケジュール値引きとの比較（`services/schedule_comparison.py`）

§1の企画の出発点（値引きのタイミングが「19時=3割引・20時半=半額」で固定化されていて
機会損失・廃棄ロスが起きている）を、実際の数字で裏付けるための機能。動的値引き
（`services/simulation.py`の`run_simulation`）と**同じ乱数シード**で、固定スケジュールの
値引きポリシーによるシミュレーションを別に走らせ、両者の結果を比較する。

**固定スケジュールの値引きタイミング**：`services/simulation.py`とは独立した2つのステップ定数
（`FIXED_SCHEDULE_30_STEP` / `FIXED_SCHEDULE_50_STEP`）で決める。`frontend/src/lib/clock.ts`の
`stepToClockTime`（営業時間10:00〜22:00・40ステップの換算。2026-11-26改訂）を逆算した固定値：

```
19:00 → (19:00 − 10:00) ÷ (22:00 − 10:00) × 40 = 540 ÷ 720 × 40 = 30
20:30 → (20:30 − 10:00) ÷ (22:00 − 10:00) × 40 = 630 ÷ 720 × 40 = 35
```

**2026-11-26追加**：実際の売り場の手順に合わせ、21時を過ぎたステップ
（`FIXED_SCHEDULE_ZUBARI_STEP = ZUBARI_START_STEP = 37`）でズバリ引きにする。固定スケジュール側は
売れ行きを見ないので、下限（75%引き）まで一気に下げる。

ステップが`FIXED_SCHEDULE_30_STEP`（30）に達したら30%引き、`FIXED_SCHEDULE_50_STEP`（35）に
達したら半額（50%引き）。時刻だけで機械的に決まり、動的値引きのような「事後分布」「実際の
遅れ」といった判断は一切使わない（これが固定スケジュールの特徴そのもの）。一度上がったら
下がらない、という制約は時刻だけで単調に決まるため自然に満たされる

**処理**（1商品ぶん。純関数。DBもネットワークも触らない）

1. `services/simulation.py`の`_sample_poisson`・`discount_multiplier`（値引き感度の非線形式。
   §5.3）をそのまま使い回す（購入生成・ガンマ-ポアソン更新のロジックを重複させない）
2. 値引き率だけを`_fixed_schedule_rate(step)`（時刻ベースの固定値）に差し替える。
   目標廃棄率は使わない（固定スケジュール側には「目標」という概念自体が無い）
3. 動的値引きの`run_simulation`と同様、在庫が0（完売済み）になったステップ以降は
   購入生成・事後分布の更新を止める（§5.2 step2bと同じ、打ち切りデータの扱い）
4. 動的値引き側と**同じ乱数シード**（`f"{seed}-{product_id}"`）で商品ごとの乱数列を作る。
   両者は最初は同じ乱数列から出発するが、値引き率が違えば生成される購入個数も変わるため、
   最初に差が出たステップ以降は乱数の消費のされ方が変わり、2つのシミュレーションは
   自然に分岐していく（同じ「その日の運」から出発した別のシナリオ、という位置づけ）

**出力**：`POST /api/compare`（`routers/comparison.py`）。リクエストは`POST /api/simulations`と
同じ4項目（天気・曜日・イベント有無・目標廃棄率）。レスポンスは商品ごとに
`{product_id, product_name, unit_price, dynamic_steps, dynamic_final_waste_rate,
fixed_steps, fixed_final_waste_rate}`（`*_steps`は`{step, quantity, remaining_stock,
recommended_rate}`の配列）、加えて`fixed_schedule_30_step` / `fixed_schedule_50_step`
（画面のグラフに縦線を引くため）を含める。**DBには一切書き込まない**：
`SimulationRun`・`PurchaseLog`・`DiscountRecommendation`・`SimulationResult`のいずれも作らず、
「学習の継続」（`Product.prior_demand`の書き戻し）も「在庫の自動調整」（§5.7）も発生しない
（一過性の比較であり、確定した実績として履歴に残す性質のものではないため）。推定売上は
返さない（`unit_price`と`*_steps`を返すので、フロントの`lib/revenue.ts`の`computeRevenue`を
そのまま使い回して画面側で計算する。バックエンドとフロントで売上計算ロジックを重複させない）
**エラー時**：商品が1件も登録されていなければ500（`POST /api/simulations`と同じ扱い）。
初期在庫0の商品は結果から除外する（`run_simulation`の`active_products`フィルタと同じ）

### 5.10 値引きタイミングの傾向分析（`services/discount_timing.py`）

過去の全シミュレーション履歴から、天気・曜日・イベント有無の条件ごとに、値引きが平均何
ステップ目から始まっているかを集計する。新しいテーブルは作らない（既存の`SimulationRun`・
`SimulationResult`・`DiscountRecommendation`から集計する読み物。`/opportunities`・
`/overstock`と同じ方針）。

**入力**：完了済み（`status = "finished"`）の`SimulationRun`全件と、それに紐づく
`SimulationResult`（＝「このrunでこの商品が対象だった」という組を数え上げるため。
`/opportunities`・`/overstock`と同じ理由でこのテーブルを使う）・`DiscountRecommendation`

**処理**（1つの`(run_id, product_id)`の組ぶん。純関数）

1. その組の`DiscountRecommendation`のうち、`recommended_rate > 0`の最初の行の`step`を
   「初回値引きステップ」とする。`DiscountRecommendation`は値引き率が変化した瞬間だけを
   記録している（§5.2 step2c）ため、`recommended_rate > 0`の最小`step`がそのまま
   「値引きが必要になった最初のステップ」になる
2. 該当する行が1つも無ければ、その組は「値引きが一度も発生しなかった」として扱う
   （初回値引きステップは無し）

**集計**：`SimulationRun`の`(weather, day_type, has_event)`の組み合わせ（12通り）ごとに、
該当する`(run_id, product_id)`の組を集める：

- `sample_count`：該当する組の総数
- `discounted_count`：そのうち値引きが1回でも発生した組の数
- `avg_first_discount_step`：値引きが発生した組だけの初回値引きステップの平均
  （`discounted_count = 0`なら`null`）

**削除済み商品の扱い**：`/opportunities`・`/overstock`と異なり、この分析は商品ごとではなく
**天気・曜日・イベント有無の条件ごと**に集計するため、削除済み商品の`SimulationResult`も
集計に含める（商品自体の情報は表示しないため、削除済みでも「その日その条件で値引きが
どうだったか」というデータとしては有効）

**出力**：`GET /api/discount-timing` → `{conditions: [{weather, day_type, has_event,
sample_count, discounted_count, avg_first_discount_step}, ...]}`。**該当する完了済みrunが
1件も無い条件は結果の配列に含めない**（画面側で「データなし」の12マス目のグリッドに
組み立て直す。§4⑦）
**エラー時**：完了済みの`SimulationRun`が1件も無ければ、`conditions: []`を返す（エラーにしない）

## 7. 受け入れ条件

- [ ] `営業開始` を押すとシミュレーションが自動進行し、画面が購入ログの発生に合わせてリアルタイムに更新される
- [ ] 天気を「雨」にすると「晴れ」より基準需要（λ）が下がり、より早いステップで値引き提案が出る
- [ ] 目標廃棄率を画面で変更すると、同じ条件でも提案される値引き率の計算結果が変わる
- [ ] 同じ `SimulationRun.id` からシミュレーションを実行すると、乱数が決定的になり毎回同じ購入ログ・結果になる
- [ ] シミュレーション終了後、各商品の実績廃棄率と目標達成可否が表示され、`SimulationResult` として保存される
- [ ] 在庫の自動調整（§5.7）で`Product.initial_stock`が変わったあとに`/opportunities`・`/overstock`を見ても、調整前に実行した過去のrunの判定結果が変わらない（`SimulationResult.initial_stock`のスナップショットを見るため）
- [ ] `/history` で過去の回を選ぶと、その回の値引き率推移グラフ（商品別）が表示される
- [ ] 各商品（seedは12件）それぞれ独立に値引き提案が計算され、互いに影響しない
- [ ] **商品の種類（§2.1）**：seed投入後の`GET /api/products`は12件を返し、各商品に`category`
      （`弁当・丼`／`揚げ物の単品`／`軽食・つまみ`）が付いている。`/products`の追加・編集フォームで
      種類を選べ、一覧に種類が表示される。3種類以外の値をAPIに送ると422になる
- [ ] `/products` で基準需要を入力して商品を追加すると、一覧に12条件ぶんの事前分布が
      自動生成された状態で追加される（天気「晴れ」は「雨」より基準需要が高い値になる）
- [ ] 追加した商品は `/` のシミュレーション画面にもカードが増え、他商品と同様に値引き提案が計算される
- [ ] 商品を削除すると一覧から消える。削除しても、その商品を含む過去のシミュレーション履歴の
      表示はエラーにならない（商品名が「?」になるだけ）
- [ ] `/opportunities` は、値引きを一度もせず閉店3ステップ以上前に完売した商品だけを対象にし、
      推奨追加在庫数の平均が大きい順に最大10件表示する
- [ ] 一度でも値引きされた商品や、閉店間際（37ステップ超）に完売した商品は `/opportunities` の対象外になる
- [ ] 該当する商品が無ければ「値引きなしで早期完売した商品はまだありません。」と表示される（エラーにしない）
- [ ] `/products` で商品を編集して基準需要を変えると、12条件ぶんの事前分布が新しい値で作り直される
- [ ] 編集フォームを開いたとき、基準需要の初期値は保存済みの事前分布から逆算した値になる
- [ ] シミュレーション実行中、在庫推移グラフが商品ごとの残り在庫数を折れ線で表示し、
      ステップが進むごとに描画範囲が伸びていく（開始前は表示されない）
- [ ] **学習の継続**：同じ条件（天気・曜日・イベント有無）で1回目のシミュレーションを実行した後、
      同じ条件で2回目を実行すると、2回目の該当商品の開始時の事後分布（α, β）は
      1回目終了時点の事後分布と一致する（`/products` を見ると、その条件のα/βが変化している）
- [ ] 異なる条件でシミュレーションを実行しても、他の11条件の事前分布（α, β）は変化しない
- [ ] 商品を編集（基準需要を変更して保存）すると、学習で更新されていた事前分布も含めて
      12条件ぶん作り直され、学習内容はリセットされる
- [ ] **連続実行**：回数を3にして `連続実行` を押すと、`POST /api/simulations` が3回直列で
      呼ばれ（前の回の完了を待ってから次が呼ばれる）、完了後に学習曲線グラフ（3点、商品ごとに
      色分け）が表示される。`/history` には3回ぶんが個別の記録として残る
- [ ] 連続実行の途中でエラーが起きたら、その時点で打ち切ってエラーメッセージを表示する
      （それまでに成功した回の履歴は残る）
- [ ] 連続実行中は `営業開始` ・ `連続実行` の両方のボタンが無効化される
- [ ] 連続実行で学習曲線グラフが表示された状態で `営業開始`（単発実行）を押すと、
      学習曲線グラフは消える
- [ ] **CSVエクスポート**：`/history` で `CSVダウンロード` を押すと、一覧に出ている実行回数 ×
      商品数ぶんの行を持つCSVがダウンロードされる。1行目はヘッダー
      （`実行ID,日時,天気,曜日,イベント,目標廃棄率(%),商品名,実績廃棄率(%),達成可否`）
- [ ] 商品が1件も無い回があっても、その回の行（商品名・実績廃棄率・達成可否は空欄）は出力され、
      回自体が欠落しない
- [ ] **履歴の条件フィルタ**：天気を「雨」に絞ると、天気が雨の回だけが一覧に表示される。
      天気「雨」・曜日「休日」のように複数条件を組み合わせるとAND（両方満たす回だけ）になる
- [ ] フィルタで0件になったら「条件に一致する実行履歴がありません。」と表示され、
      `CSVダウンロード`ボタンは無効化される
- [ ] フィルタを適用した状態で`CSVダウンロード`を押すと、絞り込み後の行だけがCSVに出力される
      （フィルタ前の全件ではない）
- [ ] **過剰在庫分析**：`/overstock` は、最大値引き（75%）が一度でも提案されたのに終了時点で
      売り切れなかった商品だけを対象にし、推奨削減在庫数の平均が大きい順に最大10件表示する
- [ ] 最大値引きに達しないまま終了した商品（値引きが弱いまま余った）や、最大値引きに達したが
      結局完売した商品は `/overstock` の対象外になる
- [ ] 該当する商品が無ければ「値引き上限まで下げても売れ残った商品はまだありません。」と
      表示される（エラーにしない）
- [ ] **分析結果バナー**：機会損失・過剰在庫のどちらかが1件以上あるとき、`/products`など
      どのページを開いていてもナビゲーション下にバナーが表示される。両方0件のときは
      バナーが表示されない
- [ ] バナーの`詳しく見る →`を押すと、対応する分析画面（`/opportunities`または`/overstock`）に
      遷移する
- [ ] `/api/opportunities`・`/api/overstock`のどちらかの取得に失敗しても、アプリ全体は
      正常に表示され続ける（失敗した方のバナー行だけ出ない）
- [ ] **単価と推定売上**：`/products`で単価を設定した商品はシミュレーション終了後に推定売上が
      表示され、未設定の商品には表示されない
- [ ] 推定売上の計算は、値引き提案が決まった次のステップから新しい値引き率を適用する
      （決まったそのステップにはまだ適用しない。§5.2と同じ順序）

- [ ] **ダークモード**：保存済みの選択が無い状態でOSがダークモードなら、初期表示はダークモードになる
