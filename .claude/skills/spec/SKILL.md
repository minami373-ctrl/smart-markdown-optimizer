これから開発する成果物の**仕様書**を `docs/spec.md` として作成します。フル版では
要件定義・基本設計・詳細設計に分かれていますが、ここでは **1 枚に統合**します。実装より先に
「何を作るか」を文章とデータで固定する、という役割は同じです。

引数（このスキルに渡された「作りたいものの一言説明」）があれば、それを出発点にする。
無ければ、まず「何を作りたいですか？」と一言で聞くところから始める。

## 手順

1. 作りたいものの種をもとに、不明点を **3〜5 個だけ** 質問する（多すぎない）。最低限、
   利用者と目的 / 主要機能 / 技術スタック / 今回やらないこと を確定させる。
2. `docs/spec.md` を下の構成で作成する。埋められない箇所は仮で埋め「※要確認」を付す。
3. 作成後、受け入れ条件を読み上げ「この 1 項目がそのままテストになります」と伝え、
   問題なければ `feature` スキルに進むよう促す。

## docs/spec.md の構成

```
# 仕様書：<プロジェクト名>

## 1. 概要 / 目的
- 何のアプリか、誰が何のために使うか（3〜5 行）

## 2. スコープ
- やること / やらないこと（今回対象外）

## 3. 技術スタック
- 言語 / フレームワーク / テストランナー（それぞれ 1 つに絞る）

## 4. 画面（または CLI）仕様
画面・コマンドごとに：目的 / 表示・入出力する要素 / 操作とその結果 / 遷移

## 5. 処理フロー
主要な処理ごとに「入力 → 処理 → 出力・保存」。分岐とエラー時の挙動も書く。

## 6. データモデル
| 項目 | 型 | 必須 | 制約・説明 |
（AI がスキーマを勝手に創作しないよう、ここを明示する）

## 7. 受け入れ条件
「正しく動く」と言える条件を、検証できる形の箇条書きで。
- [ ] 〜のとき、〜になる
（曖昧な "正しく動く" は不可。この 1 項目が 1 テストになる）
```

ハッカソンで一周できる規模（画面 3〜4 枚 / 受け入れ条件 5〜8 個）に抑えること。
