`docs/spec.md` を唯一の正として、以下を自律的に進めてください。各ステップの前に、
何をなぜするのかを 1〜2 文で声に出してから動くこと。

## 事前確認

- `docs/spec.md` を読む。無い、または受け入れ条件が空なら、進めず
  「先に spec スキルで仕様書を作ってください」と伝えて停止する。

## 1. ヒアリング

追加したい機能を聞き、`docs/spec.md` と照合して整合を確認する。仕様に無いことを
足す必要が出たら、実装より先に `docs/spec.md` を更新する。

## 2〜4 のループ（未達の受け入れ条件が無くなるまで繰り返す）

### 2. 実装
まだ満たしていない受け入れ条件を 1 つ選び、それを満たす最小限のコードを書く。

### 3. コードレビュー修正ループ
`code-reviewer` サブエージェントを起動して、今回の変更をレビューさせる。
（起動前に一言：「レビューは別コンテキストで走るので、メインの文脈は汚れません」）
- **継続**: 致命的・高の指摘が 1 件以上 → メインがコードを修正して再レビュー
- **正常終了**: 致命的・高がゼロ → 次へ
- **異常終了**: 3 周直しても残る → 停止し、残った指摘を人間に提示して判断を仰ぐ
- レビュアーはコードを編集しない。**修正は必ずメイン（あなた）が行う。**

### 4. テスト
選んだ受け入れ条件に対応するテストを書き、実行する。失敗は T / I / E に分類して扱う：
- **T（テスト側の不備）** → テストを直して再実行（最大 3 周）
- **I（実装バグ疑い）** → 人間へ報告して停止（**期待値を緩めて隠さない**）
- **E（環境・依存・データ）** → 人間へ報告して停止

T が 3 周で緑にならなければ I を疑い、人間へ上げて止める。

## 完了時のまとめ

- 満たした受け入れ条件の一覧とテスト結果（緑の数）
- レビューで何を指摘され、どう直したか（＝AI が自分で検証して自分で直した箇所）
- 仕様と実装がズレかけた瞬間があれば、どこで気づいてどう戻したか
